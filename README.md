패킷이 **수신 → 배치 송신**까지 흐르는 단일 파이프라인이고, 위 3가지 실험은 이 흐름의 서로 다른 지점에 위치합니다.

- **계층 분리** — 워커 스레드(= CPU 코어 수)는 수신·파싱만 담당하고, 게임 상태는 33ms(≈30Hz) 틱을 도는 **단일 로직 스레드가 단독 소유**합니다. 덕분에 플레이어·총알 상태에 락이 필요 없습니다.
- **서버 권위** — 클라이언트는 입력 키만 보내고 이동·충돌·시야 판정은 서버가 합니다. AOI는 공간 그리드로 **주변 이웃 셀만 계산**해 전송합니다.

## 1. I/O 모델 벤치마크 — IOCP vs WSAPoll

IOCP가 게임 서버의 표준처럼 쓰이지만, 실제로 WSAPoll과 얼마나 차이가 나는지 직접 확인하고 싶었습니다.

두 방식으로 서버를 각각 구현하고, **동시 접속 500 → 5,000봇**으로 부하를 점차 올리며 60초 평균 틱 타임을 측정했습니다.

### ⚠️ 문제점 (예상과 다른 첫 결과)

IOCP가 동접이 늘수록 유리할 거라 예상했지만, 첫 측정에서는 **500~5,000 전 구간에서 WSAPoll이 2배 이상 빠르게** 나왔습니다.

### 🔍 원인 분석 (I/O 모델이 아니라 '송신 방식')

코드를 다시 뜯어보니 두 서버의 **송신 시점이 서로 달랐습니다.**

- **IOCP** — 패킷이 생길 때마다 즉시 `WSASend` (세션당 틱마다 여러 번)
- **WSAPoll** — 틱 동안 버퍼에 모았다가 한 번에 전송 (세션당 틱마다 1회)

즉 비교 대상(I/O 모델)이 아닌 **송신 방식이라는 숨은 변수**가 결과를 지배하고 있었습니다.

### ✅ 조건을 통일한 뒤 재측정

두 서버를 **모두 배치 송신으로 통일**하고 다시 측정한 결과, 전 구간에서 IOCP가 더 낮은 틱 타임을 보였고 **부하 증가에 따라 IOCP가 WSAPoll 대비 6.8% ~ 12.3% 우수한 성능을 보였습니다.**



| 동접(봇) | WSAPoll | IOCP | 격차(ms) | 격차 % |
| --: | --: | --: | --: | --: |
| 500 | 14.09 | 13.14 | **+0.96** | 6.8% |
| 1,000 | 31.53 | 28.92 | **+2.61** | 8.3% |
| 2,000 | 56.53 | 51.33 | **+5.21** | 9.2% |
| 3,000 | 88.66 | 77.99 | **+10.68** | 12.0% |
| 4,000 | 121.02 | 108.07 | **+12.96** | 10.7% |
| 5,000 | 151.41 | 132.81 | **+18.60** | 12.3% |

<sub>단위 ms · 동일 부하 60초 측정</sub>

### 💡 배운 점

이번 실험에서 가장 큰 수확은 IOCP가 더 빠르다는 결론이 아니라 **벤치마크에서는 비교 대상 외의 변수를 먼저 통제해야 한다는 점**이었습니다.

첫 번째 결과만 보고 결론을 내렸다면 잘못된 판단을 했을 것이고, 코드를 다시 분석하면서 병목이 I/O 모델이 아니라 송신 방식에 있다는 것을 확인할 수 있었습니다.

<details>
<summary><b>📄 즉시 송신 vs 배치 송신 — 코드로 보기</b></summary>

<br/>

**Before — 패킷마다 즉시 송신**

```cpp
// 패킷이 생길 때마다 그 자리에서 WSASend 발생
void postSend(Session* s, const char* data, int len) {
    s->sendBuffer.Write(data, len);
    flushSend(s);              // ← 즉시 전송
}
```

**After — 틱 동안 모아서 세션당 1회 전송**

```cpp
// 틱 도는 동안엔 버퍼에 쓰기만, "보낼 목록"에 세션을 한 번만 등록
void queueSend(Session* s, const char* data, int len) {
    s->sendLock.lock();
    s->sendBuffer.Write(data, len);
    s->sendLock.unlock();

    if (!s->sendDirty) {       // 중복 등록 방지
        s->sendDirty = true;
        g_pendingSend.push_back(s->index);
    }
}

// 틱 끝에 딱 한 번 송신
void FlushPending() {
    for (int idx : g_pendingSend) {
        Session* s = &g_sessions[idx];
        s->sendDirty = false;
        flushSend(s);          // 실제 전송은 여기서 딱 한 번
    }
    g_pendingSend.clear();
}
```

게임 로직 스레드는 틱 끝에서 `FlushPending()`만 호출합니다.

```cpp
while (true) {
    // recv 드레인 → World::Update (내부에서 queueSend 여러 번)
    ...
    FlushPending();   // 틱 동안 쌓인 걸 세션당 1회로 flush
    std::this_thread::sleep_until(tickStart + 33ms);
}
```

## 2. 스레드 간 전달 큐 — 더블 스왑 버퍼 vs 이벤트 큐 

Go에서 채널을 자주 사용했기 때문에 C++에서도 std::queue + std::mutex 기반 이벤트 큐로 워커 스레드 → 게임 스레드 간 패킷을 전달했습니다.

### ⚠️ 문제점 (평균은 괜찮았지만 순간적인 프레임 스파이크)

평균 틱에서는 문제가 없었습니다. 문제는 테스트 봇을 동시에 접속시키는 순간이었습니다. 봇들이 한꺼번에 패킷을 쏟아내자 특정 틱에서 큰 스파이크가 생겼습니다.

### 🔍 원인 분석 (메시지당 락 경합)

소비자인 게임 스레드는 `while(Pop())`으로 **메시지 하나당 락을 한 번씩** 잡는데, 그동안 워커 스레드들도 계속 `Push`하며 **같은 뮤텍스 하나를 두고 경합**하고 있었습니다. 부하가 커질수록 락 경합도 늘어나는 구조였습니다.

### ✅ 해결 (더블 스왑 버퍼)

"어쩔 수 없다"라며 넘기려다 락을 최소화할 방법을 찾던 중 더블 스왑 버퍼를 알게 됐습니다. 

게임 스레드는 **프레임당 `Swap()` 한 번**으로 Back 버퍼를 통째로 가져오고 Front 버퍼는 읽기만, Back 버퍼는 쓰기만 진행합니다.

메인 게임 쓰레드의 패킷 처리는 락없이 진행됩니다. 스왑은 포인터만 교체하는 **O(1)** 이라, 락 유지 시간도 배치 크기와 무관하게 일정합니다.


| 지표 | 이벤트 큐 | 더블 스왑 | 개선 |
| :-- | --: | --: | :-- |
| avg | 15.64 | 13.14 | – |
| p50 | 13.49 | 12.28 | – |
| **p99** | 41.83 | 21.83 | 예산 초과 → **이하** |
| **p99.9** | 77.84 | 28.91 | 예산 초과 → **이하** |
| **max** | 83.93 | 49.62 | **−41%** |

<sub>단위 ms · 동일 부하 60초 측정</sub>

소비자 쪽 락 획득이 **메시지당 → 프레임당**으로 줄면서, **피크 프레임 타임(max)이 83.9ms → 49.6ms**, **p99가 41.8ms → 21.8ms**로 절반 가까이 떨어졌습니다. 이벤트 큐에서 **33ms 예산을 넘던 p99·p99.9가 더블 스왑에서는 예산 안으로 들어왔습니다.**

### 💡 배운 점
처음에는 평균 틱 타임만 측정하면 충분하다고 생각했습니다. 

하지만 평균은 순간적으로 발생하는 틱 지연을 보여주지 못했고, 문제를 추적하는 과정에서 p99, p99.9 같은 실무에서 사용한다는 꼬리 지표를 알게 되었습니다. 

실제로 33ms(30Hz) 예산을 초과해 렉을 만드는 원인은 평균이 아니라 일부 프레임의 긴 지연이었고, 이후부터는 평균뿐 아니라 p99를 함께 확인하며 성능을 분석하게 되었습니다.

<details>
<summary><b>📄 더블 스왑 버퍼 — 코드로 보기</b></summary>

<br/>

```cpp
template<typename T>
class DoubleBuffer {
    std::vector<T> back;    // 워커들이 쓰는 쪽
    std::mutex     lock;
public:
    void Push(T item) {                              // 생산자: Back에만 append
        std::lock_guard<std::mutex> g(lock);
        back.push_back(std::move(item));
    }
    void Swap(std::vector<T>& out) {                 // 소비자: 프레임당 1회
        std::lock_guard<std::mutex> g(lock);
        std::swap(back, out);                        // O(1) — 내부 포인터만 교환
    }
};

// 소비: 메시지 N개 → 락 1번, 처리 구간은 lock-free
buffer.clear();
g_recvQueue.Swap(buffer);   // 여기서만 락
for (auto& p : buffer) {    // 이 루프 전체가 락 없이 동작
    process(p);
}
```

</details>
