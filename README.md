**계층 분리** · 워커 스레드(= CPU 코어 수)는 수신·파싱만 담당하고, 게임 상태는 33ms(≈30Hz) 틱을 도는 **단일 로직 스레드가 단독 소유**합니다. 덕분에 플레이어·총알 상태에 락이 필요 없습니다.

**서버 권위** · 클라이언트는 입력 키만 보내고 이동·충돌·시야 판정은 전부 서버가 수행합니다. 클라이언트를 신뢰하지 않습니다.

**오브젝트 풀** · 세션·총알처럼 수명이 짧고 수정이 잦은 객체는 고정 크기 풀에서 **정수 인덱스로 O(1) 할당·반납**합니다. 런타임 중 힙 할당으로 인한 alloc/free 비용과 파편화를 방지했습니다.

**AOI (관심 영역)** · 맵 전체 객체를 순회하는 대신, 공간 그리드를 기반으로 **플레이어 주변 3×3 셀의 후보 객체만 검색**한 후 시야 판정을 수행합니다. 이를 통해 브로드캐스트 패킷 전송량과 서버 계산 연산량을 크게 줄였습니다.

## 1 · I/O 모델 벤치마크 — IOCP vs WSAPoll

> **한줄 요약** — 처음 측정에서는 예상과 달리 WSAPoll이 더 빠르게 나왔습니다. 코드를 다시 확인해 보니 I/O 모델이 아니라 송신 방식이 서로 달랐고, 이를 동일하게 맞춘 뒤 다시 측정하자 IOCP가 6.8~12.3% 더 낮은 틱 타임을 보였습니다.

대부분의 게임 서버 포트폴리오에선 IOCP를 사용합니다. 저는 IOCP가 Polling과 실제 성능 차이가 얼마나 나는지 궁금해졌고, 동일한 서버를 두 방식으로 구현해 비교했습니다. **동시 접속 500 → 5,000봇**으로 부하를 점차 올리며 각각 60초 평균 틱 타임을 측정했습니다.

**문제 · 예상과 다른 첫 결과**
IOCP가 동접이 늘수록 유리할 거라 예상했지만, 첫 측정에서는 **500~5,000 전 구간에서 WSAPoll이 2배 이상 빠르게** 나왔습니다.

**원인 분석 · I/O 모델이 아니라 '송신 방식'**
코드를 다시 뜯어보니 두 서버의 **송신 시점이 서로 달랐습니다.**

- `IOCP` — 패킷이 생길 때마다 즉시 `WSASend` (세션당 틱마다 여러 번)
- `WSAPoll` — 틱 동안 버퍼에 모았다가 한 번에 전송 (세션당 틱마다 1회)

즉 비교 대상(I/O 모델)이 아닌 **송신 방식이라는 숨은 변수**가 결과를 지배하고 있었습니다.

**해결 · 조건을 통일한 뒤 재측정**
두 서버를 **모두 배치 송신으로 통일**하고 다시 측정한 결과, 전 구간에서 IOCP가 더 낮은 틱 타임을 보였고 부하 증가에 따라 IOCP가 WSAPoll 대비 **6.8% ~ 12.3% 우수**한 성능을 보였습니다.

| 동접(봇) | WSAPoll | IOCP | 격차(ms) | 격차 % |
| --: | --: | --: | --: | --: |
| 500 | 14.09 | 13.14 | **+0.96** | 6.8% |
| 1,000 | 31.53 | 28.92 | **+2.61** | 8.3% |
| 2,000 | 56.53 | 51.33 | **+5.21** | 9.2% |
| 3,000 | 88.66 | 77.99 | **+10.68** | 12.0% |
| 4,000 | 121.02 | 108.07 | **+12.96** | 10.7% |
| 5,000 | 151.41 | 132.81 | **+18.60** | 12.3% |

<sub>단위 ms · 동일 부하 60초 측정</sub>

**배운 점**
가장 큰 수확은 IOCP가 더 빠르다는 결론이 아니라 **벤치마크에서는 비교 대상 외의 변수를 먼저 통제해야 한다는 점**이었습니다. 첫 번째 결과만 보고 결론을 내렸다면 잘못된 판단을 했을 것이고, 코드를 다시 분석하면서 병목이 I/O 모델이 아니라 송신 방식에 있다는 것을 확인할 수 있었습니다.

<details>
<summary><b>즉시 송신 vs 배치 송신 — 코드로 보기</b></summary>

<br/>

**Before — 패킷마다 즉시 송신**

```cpp
// 패킷이 생길 때마다 그 자리에서 WSASend 발생
void postSend(Session* s, const char* data, int len) {
    s->sendBuffer.Write(data, len);
    flushSend(s);              // ← 즉시 전송
}
```

**After — 틱 동안 모아서 세션당 1회 전송**

```cpp
// 틱 도는 동안엔 버퍼에 쓰기만, "보낼 목록"에 세션을 한 번만 등록
void queueSend(Session* s, const char* data, int len) {
    s->sendLock.lock();
    s->sendBuffer.Write(data, len);
    s->sendLock.unlock();

    if (!s->sendDirty) {       // 중복 등록 방지
        s->sendDirty = true;
        g_pendingSend.push_back(s->index);
    }
}

// 틱 끝에 딱 한 번 송신
void FlushPending() {
    for (int idx : g_pendingSend) {
        Session* s = &g_sessions[idx];
        s->sendDirty = false;
        flushSend(s);          // 실제 전송은 여기서 딱 한 번
    }
    g_pendingSend.clear();
}
```

게임 로직 스레드는 틱 끝에서 `FlushPending()`만 호출합니다.

```cpp
while (true) {
    // recv 드레인 → World::Update (내부에서 queueSend 여러 번)
    ...
    FlushPending();   // 틱 동안 쌓인 걸 세션당 1회로 flush
    std::this_thread::sleep_until(tickStart + 33ms);
}
```

## 2 · 스레드 간 전달 큐 — 더블 스왑 버퍼 vs 이벤트 큐

> **한줄 요약** — 평균 틱 타임만 봐서는 더블 스왑 버퍼와 이벤트 큐 둘 다 문제가 없어 보였지만 동시 접속 순간 락 경합으로 큰 스파이크가 발생했습니다. 더블 스왑 버퍼를 적용한 뒤 p99가 41.8ms → 21.8ms로 감소했습니다.

평소 Go 언어에서 채널을 자주 사용했기 때문에 C++에서도 `std::queue + std::mutex` 기반 이벤트 큐로 워커 스레드 → 게임 스레드 간 패킷을 전달했습니다.

**문제 · 평균은 괜찮았지만 순간적인 프레임 스파이크**
평균 틱에서는 문제가 없었습니다. 문제는 테스트 봇을 **동시에 접속시키는 순간**이었습니다. 봇들이 한꺼번에 패킷을 쏟아내자 특정 틱에서 큰 스파이크가 생겼습니다.

**원인 분석 · 메시지당 락 경합**
소비자인 게임 스레드는 `while(Pop())`으로 **메시지 하나당 락을 한 번씩** 잡는데, 그동안 워커 스레드들도 계속 Push하며 같은 뮤텍스 하나를 두고 경합하고 있었습니다. 부하가 커질수록 락 경합도 늘어나는 구조였습니다.

**해결 · 더블 스왑 버퍼 적용 후 재측정**
게임 스레드는 프레임마다 `Swap()`으로 두 버퍼를 교체한 뒤 메인 로직 스레드는 Front 버퍼를 읽기만, 워커들은 Back 버퍼에 쓰기만 진행합니다. 패킷 처리는 **락 없이** 진행되고, 스왑은 포인터만 교체하는 **O(1)**이라 락 유지 시간도 배치 크기와 무관하게 일정합니다.

| 지표 | 이벤트 큐 | 더블 스왑 | 개선 |
| :-- | --: | --: | :-- |
| avg | 15.64 | 13.14 | – |
| p50 | 13.49 | 12.28 | – |
| **p99** | 41.83 | 21.83 | 예산 초과 → **이하** |
| **p99.9** | 77.84 | 28.91 | 예산 초과 → **이하** |
| **max** | 83.93 | 49.62 | **−41%** |

<sub>단위 ms · 동일 부하 60초 측정</sub>

소비자 쪽 락 획득이 **메시지당 → 프레임당**으로 줄면서 피크 프레임 타임(max)이 83.9 → 49.6ms, p99가 41.8 → 21.8ms로 절반 가까이 떨어졌습니다. 이벤트 큐에서 **33ms 예산을 넘던 p99·p99.9가 예산 안으로** 들어왔습니다.

**배운 점**
처음에는 평균 틱 타임만 측정하면 충분하다고 생각했습니다. 하지만 평균은 순간적인 틱 지연을 보여주지 못했고, 문제를 추적하며 **p99, p99.9 같은 꼬리 지표**를 알게 되었습니다. 실제로 33ms(30Hz) 예산을 초과해 렉을 만드는 원인은 평균이 아니라 일부 프레임의 긴 지연이었고, 이후부터는 평균뿐 아니라 p99를 함께 확인하게 되었습니다.

<details>
<summary><b>더블 스왑 버퍼 — 코드로 보기</b></summary>

<br/>

```cpp
template<typename T>
class DoubleBuffer {
    std::vector<T> back;    // 워커들이 쓰는 쪽
    std::mutex     lock;
public:
    void Push(T item) {                              // 생산자: Back에만 append
        std::lock_guard<std::mutex> g(lock);
        back.push_back(std::move(item));
    }
    void Swap(std::vector<T>& out) {                 // 소비자: 프레임당 1회
        std::lock_guard<std::mutex> g(lock);
        std::swap(back, out);                        // O(1) — 내부 포인터만 교환
    }
};

// 소비: 메시지 N개 → 락 1번, 처리 구간은 lock-free
buffer.clear();
g_recvQueue.Swap(buffer);   // 여기서만 락
for (auto& p : buffer) {    // 이 루프 전체가 락 없이 동작
    process(p);
}
```

## 3 · 수신·송신 버퍼 — 링 버퍼 vs 가변 버퍼

> **한줄 요약** — 일반적인 게임 패킷에서는 두 버퍼 모두 비슷한 성능을 보였습니다. 하지만 고정 크기 링 버퍼는 대용량 패킷에서 별도의 처리가 필요했고 가변 버퍼는 이 문제를 자연스럽게 해결했습니다. 자료구조의 성능도 물론 중요하지만 워크로드에 맞는 선택이 더 중요하다는 점을 확인했습니다.

게임 서버에서는 링 버퍼를 많이 사용하길래 저도 처음에는 링 버퍼를 적용했습니다. 그런데 실제로 얼마나 차이가 나는지 궁금했고, 동일한 조건에서 가변 버퍼를 구현해 성능과 안정성을 비교했습니다.

**예상 · 링 버퍼가 빠를 것**
링 버퍼는 재할당 없이 head/tail 포인터만 움직이니, 가변 버퍼보다 CPU 비용이 낮을 거라 예상했습니다.

**1차 결과 · 성능 차이는 거의 없음**

| 버퍼 종류 | Total Avg | sim Avg | flush Avg | p99 | max |
| :-- | --: | --: | --: | --: | --: |
| **가변 Vector 버퍼** | 21.27 | 13.06 | 8.21 | 33.40 | 60.64 |
| **고정 링 버퍼** | 21.39 | 13.17 | 8.22 | 32.39 | 64.16 |

<sub>단위 ms</sub>

틱 타임 차이는 거의 나지 않았습니다. 가변 버퍼 `std::vector`는 처음 한 번 충분한 크기로 확장된 이후에는 재할당이 거의 발생하지 않았습니다.

**재실험 · 차이가 나는 조건을 직접 만들기**
재할당이 거의 없는 워크로드라 차이가 안 나는 것 아닐까 싶었습니다. 이를 확인하려 두 버퍼 크기를 동일하게 **줄이고**, 버퍼 크기를 초과하는 큰 패킷을 반복 전송하는 악성 봇을 만들어 재실험했습니다. 의도적으로 `std::vector`가 계속 `resize()`하도록 만든 것입니다.

**트러블 · 오히려 링 버퍼에서 문제 발생**

- 링 버퍼로 구현한 서버에서는 버퍼 크기가 줄어들자 맵 일부가 로딩되지 않아 **벽이 투명해지고 충돌 판정이 사라지는 버그**가 발생했습니다.
- 게임 입장 시 전송하는 맵 스냅샷이 링 버퍼의 고정 상한을 넘자, 초과한 패킷이 버퍼에 기록되지 못하면서 **맵 스냅샷 데이터가 누락**되었고 클라이언트는 불완전한 맵을 수신했습니다.
- 같은 상황에서 가변 버퍼는 resize로 용량을 늘려 **유실 없이 맵을 온전히 전달**했습니다. 낮은 성능을 예상했던 쪽이 오히려 안정적이라는 결과가 나왔습니다.

**배운 점**

| 구분 | 고정 크기 링 버퍼 | 가변 Vector 버퍼 |
| :-- | :-- | :-- |
| **장점** | 재할당이 없어 힙 사용량이 일정하고 예측 가능 | 큰 패킷도 자동 확장으로 안정적으로 처리 |
| **단점** | 용량 초과 시 패킷 유실 가능(별도의 오버플로우 처리 필요) | 재할당 시 일시적인 메모리·복사 비용 발생 |
| **권장** | 크기가 예측 가능한 일반 게임 패킷 | 대용량 패킷 처리가 필요한 **초기화 전송 파이프라인**에 적합 |

처음에는 재할당이 없는 링 버퍼가 항상 더 좋은 선택이라고 생각했습니다. 하지만 실제로 구현하고 테스트해보니 일반적인 게임 패킷에서는 성능 차이가 거의 없었고, 오히려 맵 스냅샷처럼 큰 패킷에서는 고정 크기라는 특성이 문제가 되기도 했습니다. 이번 실험을 통해 자료구조는 이론적인 성능보다 실제 사용하는 데이터의 크기와 패턴에 맞춰 선택해야 한다는 점을 다시 한번 알 수 있었습니다.

```cpp
bool RingBuffer::Write(const char* data, int len) {
    if (len > GetFreeSize()) return false;   // ← 상한 초과 시 '이 패킷 전체'를 드랍 (부분 기록 X)

    int rightSize = BUFFER_SIZE - tail;
    if (len <= rightSize) {
        memcpy(&buffer[tail], data, len);
    } else {                                  // 끝을 넘으면 앞으로 돌아가 wrap
        memcpy(&buffer[tail], data, rightSize);
        memcpy(&buffer[0], data + rightSize, len - rightSize);
    }
    OnWrite(len);
    return true;
}
```

**가변 버퍼 — 모자라면 압축 후 resize, 항상 성공**

```cpp
bool VectorBuffer::Write(const char* data, int len) {
    Reserve(len);                            // 공간이 부족하면 확장
    memcpy(buffer.data() + tail, data, len);
    tail += len;
    return true;                             // 유실 없음
}

void VectorBuffer::Reserve(int len) {
    if (GetLinearFreeSize() >= len) return;

    int used = GetUsedSize();
    memmove(buffer.data(), buffer.data() + head, used);   // 앞으로 압축
    head = 0; tail = used;

    if (GetLinearFreeSize() < len) buffer.resize(tail + len);  // 그래도 모자라면 resize
}
```
