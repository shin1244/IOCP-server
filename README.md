## 프로젝트 개요

한 방에 최대 100명이 접속해 이동·사격하며 마지막 1인까지 생존하는 게임입니다. 방 개수는 조절할 수 있고, Go로 만든 그래픽 클라이언트로 플레이할 수 있습니다.

이 프로젝트에서는 게임 기능을 구현하면서, 서버에서 자주 쓰이는 구조가 **어떤 부하에서 효과가 있고 어떤 문제를 남기는지** 직접 확인하는 데 집중했습니다. 같은 게임 로직 위에서 I/O 모델, 스레드 간 전달 큐, 송수신 버퍼를 각각 바꿔 비교했습니다.

### 1. 송신 방식을 맞춘 뒤 I/O 모델 재비교

> **핵심:** 첫 측정에서는 WSAPoll이 빨랐습니다. 두 구현의 송신 시점이 다르다는 점을 발견하고, 배치 송신으로 통일한 뒤 다시 비교했습니다.

IOCP와 WSAPoll을 같은 서버에 각각 적용하고, 동시 접속을 500봇에서 5,000봇까지 늘리며 평균 틱 처리시간을 측정했습니다. 처음에는 모든 구간에서 WSAPoll이 2배 이상 빠르게 나왔습니다.

코드를 비교하니 I/O 모델 외에도 송신 방식이 달랐습니다.

| 첫 측정의 구현 | 송신 방식 |
| :-- | :-- |
| IOCP | 패킷이 생길 때마다 즉시 `WSASend` 호출 |
| WSAPoll | 틱 동안 데이터를 모아 세션별로 배치 송신 |

두 결과에는 I/O 모델과 송신 방식의 효과가 함께 섞여 있었습니다. IOCP 쪽도 틱 동안 송신 버퍼에 기록하고, 틱 끝에서 전송 대상 세션을 모아 flush하도록 변경했습니다.

**배치 송신으로 통일한 뒤의 결과**

| 동시 접속 봇 수 | WSAPoll 평균 | IOCP 평균 |
| --: | --: | --: |
| 500 | 14.09 | 13.14 |
| 1,000 | 31.53 | 28.92 |
| 2,000 | 56.53 | 51.33 |
| 3,000 | 88.66 | 77.99 |
| 4,000 | 121.02 | 108.07 |
| 5,000 | 151.41 | 132.81 |

<sub>단위 ms · 각 부하 구간 60초 평균</sub>

표의 평균값을 기준으로 IOCP가 약 7~12% 낮은 처리시간을 보였습니다. 이 실험을 통해 비교하려는 구조 외에 송신 빈도와 배치 방식도 먼저 맞춰야 한다는 점을 확인했습니다.

**목표 틱 예산과의 관계도 함께 봤습니다.** 제시한 IOCP 평균은 1,000봇에서 28.92ms였지만, 2,000봇부터는 33ms를 초과했습니다. 5,000봇 구간은 과부하에서의 비교 결과이며, 5,000명이 30Hz로 플레이할 수 있다는 의미는 아닙니다. 평균이 33ms 미만인 구간도 모든 틱이 예산을 지켰는지는 별도 확인이 필요합니다.

<details>
<summary>송신 시점 변경</summary>

| 단계 | 변경 전 | 변경 후 |
| :-- | :-- | :-- |
| 패킷 생성 | 송신 버퍼에 기록하고 즉시 flush | 송신 버퍼에 기록하고 전송 대상 세션 등록 |
| 같은 틱의 추가 패킷 | 패킷마다 flush 호출 | 버퍼에 추가하고 세션 중복 등록 방지 |
| 틱 종료 | 이미 개별 전송 | `FlushPending()`에서 등록된 세션별 flush |

여기서 세션별 flush는 애플리케이션의 배치 처리 단위입니다. 실제 전송 완료 처리는 비동기 송신 흐름에서 이뤄집니다.

</details>

### 2. 더블 스왑 버퍼로 소비자의 락 획득 횟수 축소

> **핵심:** 평균만으로 보이지 않던 긴 틱을 확인하고, 소비자의 락 획득을 메시지마다 한 번에서 틱마다 한 번으로 줄였습니다.

처음에는 `std::queue + std::mutex` 기반 이벤트 큐로 워커에서 게임 로직 스레드에 메시지를 전달했습니다. 평소 평균은 틱 예산 안에 있었지만, 봇을 동시에 접속시키는 구간에서 긴 지연이 나타났습니다.

소비자는 `while (Pop())`으로 메시지를 하나 꺼낼 때마다 락을 잡았고, 여러 워커도 같은 뮤텍스를 사용해 Push했습니다. 이 경합을 줄이기 위해 두 벡터를 교환하는 더블 스왑 버퍼로 바꿨습니다.

- 워커는 뮤텍스를 잡고 Back 버퍼에 메시지를 추가합니다.
- 게임 로직 스레드는 틱마다 한 번 락을 잡고 Back 버퍼와 처리용 버퍼를 교환합니다.
- 교환한 메시지는 락을 놓은 뒤 게임 로직 스레드가 처리합니다.

**생산자의 Push에는 여전히 락이 필요합니다.** 줄인 것은 소비자의 락 획득 횟수이며, 메시지 처리 루프를 공유 뮤텍스 밖으로 옮긴 구조입니다.

| 지표 | 이벤트 큐 | 더블 스왑 버퍼 |
| :-- | --: | --: |
| 평균 | 15.64 | 13.14 |
| p50 | 13.49 | 12.28 |
| **p99** | **41.83** | **21.83** |
| **p99.9** | **77.84** | **28.91** |
| 최댓값 | 83.93 | 49.62 |

<sub>단위 ms · 두 구현을 동일 부하에서 60초 측정</sub>

두 평균은 모두 33ms 안에 있었지만, 이벤트 큐의 p99와 p99.9는 예산을 넘었습니다. 변경 후에는 두 백분위수가 예산 안으로 들어왔습니다. 다만 **최댓값 49.62ms는 여전히 예산을 초과**하므로, 긴 틱이 모두 사라진 것은 아닙니다.

이후에는 평균과 함께 p99를 확인하며, 일부 틱에서 발생하는 긴 지연도 개선 대상으로 보고 있습니다.

<details>
<summary>더블 스왑 버퍼 코드</summary>

```cpp
template<typename T>
class DoubleBuffer {
    std::vector<T> back;
    std::mutex lock;

public:
    void Push(T item) {
        std::lock_guard<std::mutex> guard(lock);
        back.push_back(std::move(item));
    }

    void Swap(std::vector<T>& out) {
        std::lock_guard<std::mutex> guard(lock);
        std::swap(back, out);
    }
};

// 소비자: 이전 메시지를 비운 뒤, 틱마다 한 번 교환
buffer.clear();
g_recvQueue.Swap(buffer);

// 교환한 버퍼는 소비자만 처리하므로 이 루프에는 공유 뮤텍스가 필요 없음
for (auto& packet : buffer) {
    process(packet);
}
```

교환 시 메시지 전체를 복사하지 않고 두 벡터의 내부 저장 공간을 교환합니다. 처리할 메시지 수에 비례하는 작업은 락을 놓은 뒤 수행합니다.

</details>

### 3. 버퍼 비교에서 용량 초과 처리 누락 발견

> **핵심:** 일반 부하의 평균 처리시간 차이는 작았습니다. 큰 데이터를 보내는 조건에서는 링 버퍼의 쓰기 실패를 무시한 호출부가 문제가 됐습니다.

고정 크기 링 버퍼는 재할당 없이 head와 tail을 이동하므로, 가변 버퍼보다 비용이 작을 것으로 예상했습니다. 같은 조건에서 `std::vector` 기반 가변 버퍼와 비교했습니다.

| 버퍼 | 전체 평균 | 시뮬레이션 평균 | flush 평균 | p99 | 최댓값 |
| :-- | --: | --: | --: | --: | --: |
| 가변 Vector 버퍼 | 21.27 | 13.06 | 8.21 | 33.40 | 60.64 |
| 고정 링 버퍼 | 21.39 | 13.17 | 8.22 | 32.39 | 64.16 |

<sub>단위 ms · 두 구현을 동일 부하에서 60초 측정</sub>

이 조건에서는 가변 버퍼도 충분한 용량을 확보한 뒤 재할당이 거의 발생하지 않았고, 전체 평균은 21.27ms와 21.39ms로 가까웠습니다. 이 결과만으로 두 구조의 성능이 모든 부하에서 같다고 결론 내리지는 않았습니다.

**용량을 넘는 데이터로 재실험**

버퍼 크기를 줄이고 상한을 넘는 데이터를 전송해, 공간이 부족할 때의 동작을 확인했습니다. 링 버퍼 빌드에서는 맵 스냅샷이 정상적으로 전달되지 않아 클라이언트의 벽 표시와 충돌 관련 동작에 이상이 나타났습니다.

원인은 링 버퍼와 호출부 사이의 실패 처리였습니다. `RingBuffer::Write()`는 여유 공간이 부족하면 아무것도 기록하지 않고 `false`를 반환했지만, `queueSend()`가 그 반환값을 확인하지 않았습니다. 쓰기에 실패한 데이터가 그대로 전송에서 빠졌습니다.

<details>
<summary>용량 검사와 실패 반환값을 무시하던 호출부</summary>

링 버퍼는 전체 데이터를 기록할 공간이 없으면 쓰기를 거부합니다.

```cpp
bool RingBuffer::Write(const char* data, int len) {
    if (len > GetFreeSize()) return false;

    int rightSize = BUFFER_SIZE - tail;
    if (len <= rightSize) {
        memcpy(&buffer[tail], data, len);
    } else {
        memcpy(&buffer[tail], data, rightSize);
        memcpy(&buffer[0], data + rightSize, len - rightSize);
    }
    OnWrite(len);
    return true;
}
```

하지만 호출부는 실패 여부를 사용하지 않았습니다.

```cpp
// 문제가 발생한 호출부의 발췌
s->sendLock.lock();
s->sendBuffer.Write(data, len);  // false 반환을 확인하지 않음
s->sendLock.unlock();
```

</details>

같은 실험에서 가변 버퍼는 기존 데이터를 앞으로 압축하고 필요한 크기로 확장해 데이터를 전달했습니다. 이 사례를 통해 **버퍼 구조와 함께 용량 초과 시의 처리 정책까지 정해야 한다**는 점을 확인했습니다.

| 선택 | 얻는 점 | 함께 필요한 처리 |
| :-- | :-- | :-- |
| 고정 크기 링 버퍼 | 정해진 메모리 범위에서 재할당 없이 사용 | 쓰기 실패 확인과 대기·분할·거부 등 초과 처리 정책 |
| 가변 Vector 버퍼 | 실험의 큰 데이터를 용량 확장으로 수용 | 확장·복사 비용 측정과 메모리 사용 상한 설정 |

또한 `resize()` 호출과 실제 재할당은 구분할 필요가 있습니다. 이후 비교에서는 호출 횟수만으로 비용을 추정하지 않고, 용량 변화와 할당 횟수를 함께 기록하는 것이 과제입니다.

| 실험 재현 | 큐·버퍼 비교에도 봇 수, 방 수, 입력 빈도, 패킷 크기를 함께 명시하고 원시 로그 보존 |
| 버퍼 용량 초과 | 발견한 쓰기 실패 처리 누락에 대해 처리 정책을 정하고, 대용량 맵 전송으로 재검증 |

세 실험을 거치며 비교할 변수를 통제하고, 평균 외의 지연 분포를 확인하며, 실패 반환값까지 호출부에서 처리해야 한다는 점을 배웠습니다. 구조의 이름보다 **실제 부하와 측정 조건, 실패할 때의 동작**을 함께 설명하는 것이 중요하다고 느꼈습니다.
